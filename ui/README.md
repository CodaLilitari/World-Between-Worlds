The World Between Worlds UI is a local desktop-browser front end for the Python HTTP service. It uses system fonts, plain JavaScript, CSS, an original inline SVG wing emblem, and an original Coda illustration embedded by the local `coda-wbw.js` asset. It loads no fonts, scripts, images, analytics, or other dependencies from an external service. It has no audio playback. Original-source links are opened only by an explicit user click; external links use `noopener noreferrer`.

Serve `index.html` from the local service, replacing `{{TOKEN}}` in its `blackwing-token` meta element. Serve the assets at `/ui/styles.css`, `/ui/app.js`, and `/ui/coda-wbw.js`. The illustration script assigns a local data URL to `#coda-art`, retaining compatibility with existing updater file allowlists. Opening the HTML as a local file does not provide a working backend or security token. All API requests, including GET, carry `X-Blackwing-Token`; requests use same-origin credentials. The server remains responsible for Host/Origin validation, path validation, pinned source verification, and conversion isolation.

The primary setup asks for the Jedi Knight and Mysteries of the Sith installations. **Browse…** opens the local service's native folder chooser only after a click; typing or pasting paths remains available. Output and bulk archive folders are in initially collapsed optional settings. A blank output path uses the service's default **Documents/World Between Worlds conversions** folder. Users can choose a different folder explicitly. The dropdown is the main recipe selector, with the full card library initially collapsed to keep the first-run workflow compact. Category and gameplay filters, search, and multiple explicit selections remain available.

Each selected custom level or gameplay mod has a visible **Choose the originals** entry in the queue. **Browse original…** requests an original archive for that recipe. **Download original** opens the catalog's reviewed source page in a new tab; users download the original there and then browse to their saved ZIP or GOB. WBW does not automatically fetch the archive, attach unrelated files, or submit a conversion. Native-picker cancellation preserves existing values. A pending chooser blocks duplicate chooser requests, scans, and conversion submission; its request has no browser timeout because the user controls how long the dialog remains open. A returned archive is applied only while that same recipe remains selected and its previous file choice has not changed. If a native dialog is unavailable, the UI reports the error and leaves manual path entry available.

The initial selection is always empty. Neither loading settings nor applying filters adds a recipe. The native dropdown adds one eligible item after the user presses Add to queue. Each library card has its own checkbox. Select visible is an explicit bulk action limited to the current search/category/gameplay intersection. Selection persists across filters and is visible in the queue. Queue order follows catalog order. Unsupported content is disabled; a category with no recipes shows an explicit empty state, including singleplayer.

The browser treats recipe status `verified`, `supported`, `ready`, `available`, or `prototype` as eligible. Prototypes show their limited-compatibility status. Other or missing status tokens are not eligible. A conversion job locks its selection to avoid accidental changes during submission or execution. A rejected request unlocks the queue. If a submission response is lost, the queue stays locked and reports uncertainty instead of automatically retrying a possibly accepted conversion. A failed progress refresh provides a Retry status button and does not claim that the job stopped.

Recipe cards, the dropdown, details, and the queue display each recipe's positive integer revision as `wbw_v1`, `wbw_v2`, and so on. This is the revision of that conversion recipe, separate from the WBW application version. A catalog without revision metadata displays "Revision unavailable"; the UI does not infer a revision from a title or filename.

The **Installed levels** panel scans only after **Scan MotS folder** is clicked. It uses the current MotS path from the form, even if that path has not been saved. The service inspects GOO files and returns their recorded revisions and comparison results. The panel shows full paths, installed/catalog revisions, messages, duplicate-recipe notices, and the distinct states `current`, `update_available`, `newer`, `unversioned`, `modified`, `unrecognized`, and `error`. Truncation or per-file inspection errors mark the scan incomplete. Informational warnings, such as duplicate copies in an otherwise complete inventory, show "Scan complete with warnings". An empty incomplete scan does not claim that the folder contains no files. The scan request has a 120-second timeout for slower disks; other API requests except native pickers retain their 15-second timeout. A timeout reports failure and allows an explicit retry.

**Queue updated recipe** adds a single recognized, selectable recipe only when its scan result has `can_update: true`. **Queue all outdated** is an explicit bulk action restricted to approved `update_available` results; duplicate installed copies add only one recipe. These actions preserve existing selections and use the ordinary conversion queue. They do not start a conversion, overwrite or delete installed files, or launch/load anything. Users review their originals and output folder before clicking **Convert selected**. Scanning and installed-update actions are disabled during a conversion. Changing the MotS path invalidates prior results and discards a pending scan response; the new folder requires another explicit scan.

API contract:

| Method and path | Use |
| --- | --- |
| GET `/api/health` | Connection status; no runtime-compatibility claim. |
| GET `/api/catalog` | `{version,title,recipes:[{id,title,kind,gameplay,author,source_url,archive_hint,requires_archive,summary,status,startup_overlay,revision,revision_label}]}`. `kind` is `vanilla`, `custom`, or `mod`; `revision` is a positive integer and `revision_label` is `wbw_vN`. Display labels are derived from the integer. |
| GET `/api/settings` | Flat `jk_root`, `mots_root`, `archive_dir`, and `output_dir` strings. A `paths` wrapper is also accepted. Late responses do not overwrite fields the user already edited. |
| POST `/api/settings` | Saves those four path fields; it does not start conversion. |
| POST `/api/pick-path` | `{kind,recipe_id?}` with `kind` equal to `jk_root`, `mots_root`, `output_dir`, `archive_dir`, or `original_archive`. The last kind requires the selected `recipe_id`. Returns `{path:string|null}`; `null` means cancellation. This endpoint is called only after an explicit Browse click. |
| POST `/api/scan` | `{mots_root}`. Returns `{root,results,counts,warnings,truncated}`. Each result has `{path,filename,id,title,kind,role,installed_revision,current_revision,status,message,can_update,duplicate?}`; unmatched IDs and unavailable revisions are `null`. This is an explicit read-only inspection. |
| GET `/api/recipes/<encoded-id>` | Read-only provenance and transformation details, fetched when the user opens the details dialog. Source and returned JSON are rendered as text. |
| POST `/api/convert` | `{ids,jk_root,mots_root,archive_dir,output_dir,archives:{id:absolutePath}}`; only selected eligible IDs and their relevant original-file choices are sent. Empty `output_dir` requests the service's default output location. Returns `{job_id}`. |
| GET `/api/jobs/<encoded-id>` | `{id,status,progress,total,current,results,logs}`. `progress` means completed recipe count, not a percentage. Results can include `output`, `manifest`, `error`, and `runtime_test`. |
| POST `/api/export` | `{ids}`. The returned asset-free recipe instructions are downloaded as `wbw-recipes.json` only after the explicit export action. |

Terminal job statuses recognized by the UI are `complete`, `completed`, `done`, `success`, `succeeded`, `failed`, `error`, `cancelled`, `canceled`, and `partial`. The service should supply one of these when a job finishes. Result runtime testing is independent of conversion success: missing evidence and `not-run-on-this-output` display **Runtime test: not run on this output**. Historical catalog validation can appear in the details response and must not be supplied as a successful runtime result for a new output.

The separate Export job report action downloads the returned job JSON, including output/manifest paths and logs. It includes no game assets, but those paths/logs may be private; it performs no upload. The optional updates endpoint is not polled by this UI, and there is no invented game-launch, runtime-test, or archive-download endpoint.

Accessibility includes native form controls, explicit accessible labels, a skip link, visible keyboard focus, restored card-checkbox focus after selection, live count/status announcements, an Escape-dismissable native dialog, a slash shortcut for search outside editable controls, and reduced-motion handling. Layout breakpoints cover narrow windows and phones; the target experience is a desktop browser. These affordances require browser verification in addition to source tests.

Run UI-only tests from the repository root:

```powershell
node --test ui/test_ui.mjs
```

The tests exercise pure selection/filtering/payload logic, runtime-status separation, job-progress bounds, catalog and scan validation, qualified DOM references, token plumbing, injection-safe rendering, empty defaults, and export shape. A small DOM adapter also runs the actual application event handlers with intercepted requests to verify explicit scan/queue actions, duplicate handling, stale and pending scan invalidation, error/empty/incomplete states, conversion locks, explicit folder/original-file picker requests, cancellation, pending-picker guards, reviewed download links, and default output behavior. They launch no HTTP server, browser, native picker, converter, or game. Visual layout and actual HTTP job flow are separate integration checks performed against the backend; picker responses must be mocked during unattended browser QA.
