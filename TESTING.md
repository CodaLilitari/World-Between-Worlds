# Testing World Between Worlds

The application, conversion structure, game hosting and gameplay have separate
results. A structural pass means the generated bytes match the reviewed recipe;
it does not mean World Between Worlds has launched the game.

## Test the tool

Use a separate output folder and one or more explicitly chosen recipes. Begin
with Canyon Oasis (owned JK data only) and Jedi's High School (original custom
archive required), then inspect the generated receipts. There is no default
selection. Filtering the library does not add or remove queued entries. Select
visible is an explicit bulk action; Convert selected processes only the queue.

Check the following:

1. An empty queue cannot submit a conversion.
2. Selecting two maps produces exactly those two results.
3. A mismatched original archive stops with a useful message.
4. The game installations and original downloads remain unchanged.
5. Repeating a conversion with identical inputs and tooling produces identical
   game archive bytes. An already identical result is reused; changed existing
   output is not overwritten.
6. Each result has a recipe lock, conversion receipt, generated archive manifest
   and an independent structural verification result.
7. Export selected recipes contains only selected recipe instructions and
   provenance. Export job report is a local diagnostic report and may contain
   your selected file paths.

Source tests require no game data:

```text
python -m unittest discover -p "test_*.py"
node --test ui/test_ui.mjs
```

Node is needed only for the optional UI model tests. The application itself
does not require Node or downloaded browser libraries. Build instructions and
the updater's failure cases are documented under `packaging/`.

## Test converted maps in OpenJKDF2 MotS mode

Use a separate test installation with native MotS resources and a compatible
OpenJKDF2 build. Do not use the retail `JKM.EXE` as the test engine. Copy only
the chosen generated episode GOO to the test runtime's `episode` folder.

For maps with a required startup overlay, copy that complete generated folder
beside `episode` and `resource`, and launch from the runtime working directory:

```text
openjkdf2-64.exe -motsCompat -path bridge-<tag>-startup
```

Use the actual generated folder name. On Linux, use the equivalent OpenJKDF2
binary. Choose Multiplayer and host the converted episode. With no overlay,
launch with `-motsCompat` alone. The three stock CTF maps require `-path
bridge-ctf-ui`; their generated README describes the shared CTF setup.

Use only one gameplay overlay at a time. Restart with the matching overlay when
changing families, or restart without it for a map that needs none. Episode
selection does not unload startup inventory, player or model changes. All
multiplayer participants must use matching generated files and engine behavior.
Compatibility with an unrelated gameplay mod is a separate test.

MotS already contains a concussion rifle: inventory bin 129, bound to
`weap_concrifle_m.cog`. Existing recipes adapt JK inventory/weapon uses to MotS;
they do not remove another MotS weapon to add a duplicate concussion rifle.
Morpheus and Jawa's authored weapon changes have additional reviewed rules.

Drazen's backpack transfer requires the engine fix described in `COMMUNITY_RC1.md`.
Converting the map cannot repair an old engine executable's item-lookup bug.

Exercise actual doors, switches, elevators, pickups, traps, respawning and weapon
selection/firing. For CTF, test teams, flag pickup/drop/return, captures and score
with two players. A host surviving at its spawn does not establish these behaviors.

## Rendering and lighting

The bridge preserves source geometry, surface flags and texture references and
expands JK scalar vertex lighting into the components required by MotS. Matched
screenshots are used to look for black or unrendered surfaces, broken brightness,
missing materials and geometry failures. MotS lighting is allowed to look
different or better; pixel-for-pixel equality is not an acceptance requirement.

Known original omissions, such as Purgatory's absent `nat.mat`, stay explicitly
recorded. A textured missing-material surface cannot be called invisible or
fully restored. Comparison provenance and the actual observed test scope belong
with the screenshots, not in an unsupported blanket compatibility claim.

See `VALIDATION.md` for the measured developer runs and `COMMUNITY_RC1.md` for
the per-map adaptations and remaining gameplay checks.
